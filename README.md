# البحث العميق — HAI_SERCH

تطبيق بحث طويل المدى يعمل من السحابة ويزامن نفس المهام والنتائج بين Android وWindows.

## الهدف

- إدخال نص، صورة، أو فيديو.
- استمرار البحث حتى بعد إغلاق الأجهزة.
- تحليل بصري فعلي للصورة ولقطات الفيديو، وليس OCR فقط.
- جمع نتائج موثقة وترتيبها حسب المطابقة النصية والبصرية.
- مزامنة الطابور والمهمات السابقة والنتائج بين Android وWindows.
- VPN / Egress داخل السيرفر فقط.
- تشغيل شخصي بتكلفة أساسية 0 قدر الإمكان.

## كيف يتم تحليل الصورة والفيديو؟

### الصورة

```text
الصورة
 -> Vision محلي
 -> OCR متعدد اللغات
 -> بصمات بصرية pHash: الصورة كاملة + قصات مركزية
 -> Query Planner متعدد اللغات
 -> SearXNG (بحث ويب + صور)
 -> ميزانية مستقلة لمرشحي الصور حتى لا يقصيهم ضعف النص
 -> مقارنة صورة النتيجة بعدة بصمات كاملة/مقصوصة
 -> فحص صفحات المصادر
 -> ترتيب النتائج
```

### الفيديو

```text
الفيديو
 -> FFmpeg: لقطات عند تغيّر المشهد الحقيقي
 -> إزالة اللقطات شبه المكررة عبر pHash
 -> fallback زمني فقط إذا كانت تغيّرات المشاهد غير كافية
 -> Vision لعدد محدود من أفضل اللقطات
 -> OCR متعدد اللغات
 -> Whisper.cpp للحوار/الصوت
 -> بصمات بصرية متعددة لكل لقطة
 -> Query Planner متعدد اللغات
 -> بحث ويب + صور
 -> مقارنة صور النتائج باللقطات
 -> تحقق وترتيب
```

تحليل الوسائط والتخطيط يُحفظان في cache أثناء الحاجة إليهما لتجنب إعادة تشغيل النماذج في كل جولة. Cache تحليل الوسائط له إصدار داخلي؛ عند ترقية خوارزمية التحليل يُعاد التحليل مرة واحدة بدل الاستمرار بنتيجة قديمة.

## المطابقة البصرية

- لا يعتمد النظام على وصف Vision وحده.
- المرفق الأصلي ينتج بصمات للصورة الكاملة وقصات مركزية، وكذلك صور النتائج.
- تؤخذ أقل مسافة بين جميع بصمات المصدر والنتيجة لتحمل القص والحواف والترجمة المضافة.
- في بحث الصور/الفيديو لا يختار النظام المرشحين الأوليين بالنص فقط؛ يحجز جزءًا من نفس الميزانية لنتائج تحمل صورًا ثم يفحصها بصريًا.
- روابط المصدر تنظف من معاملات التتبع الشائعة حتى لا تُفحص نفس الصفحة عدة مرات.

## دورة حياة الصورة والفيديو

1. يرفع المرفق إلى مساحة مؤقتة مرتبطة بالحساب والمهمة.
2. يظل موجودًا فقط ما دام البحث يحتاجه. حالات `stopped` و`needs_context` تبقيه مؤقتًا حتى يمكن استئناف المهمة أو إضافة معلومة.
3. عند وصول المهمة إلى `completed` أو `partial` أو `failed` يحذف الملف الأصلي من السيرفر مباشرة ويصفّر مساره في قاعدة البيانات.
4. بعد النهاية تبقى المهمة النصية وحالتها والنتائج والمصادر فقط، ويمكن فتحها من Android أو Windows المرتبطين بنفس الحساب.
5. إذا اختار المستخدم **أرشفة** أثناء وجود المرفق، يمكن تنزيل نسخة محلية إلى الجهاز قبل إلغاء المهمة. وإذا كان المرفق قد حُذف بسبب اكتمال البحث، يحفظ الأرشيف النتائج والمصادر فقط ولا يفشل.
6. أرشيف Android مستقل عن أرشيف Windows ولا تتم مزامنته.
7. بحث نصي مكتمل يمكن متابعته لاحقًا. أما بحث صورة/فيديو بعد حذف المرفق النهائي فيحتاج رفع المرفق من جديد بدل الاحتفاظ به سرًا على السيرفر.
8. إطارات الفيديو وملفات العمل المؤقتة تحذف بعد انتهاء الحاجة إليها.
9. الرفع غير المرتبط بمهمة تنظفه الصيانة بعد TTL كشبكة أمان فقط.

## الطابور

- حد أقصى 5 مهام غير منتهية لكل حساب.
- مهمة واحدة فقط تعمل في الوقت نفسه لكل حساب.
- بقية المهام تنتظر بنظام FIFO وتبدأ تلقائيًا بعد انتهاء السابقة.
- إيقاف المهمة الأولى مؤقتًا يبقي ما خلفها في نفس الحساب في الانتظار حتى تستأنفها أو تلغيها.
- حساب آخر لا يتجمد بسبب مهمة متوقفة في حساب مختلف.
- البحث الطويل يستخدم 48 جولة بــbackoff متدرج يصل إلى 90 دقيقة، ما يعطي قرابة يومين من الزمن الجداري بدون إبقاء CPU مشغولًا طوال الوقت.

## المزامنة والتنبيهات

- Android وWindows يشتركان في نفس الحساب السحابي ونفس الطابور والنتائج.
- WebSocket يرسل تغييرات المهام مباشرة مع polling احتياطي عند انقطاع الاتصال.
- يمكن إضافة معلومة جديدة لنفس المهمة من أي جهاز ما دام السياق اللازم ما زال متاحًا؛ يرفع `context_revision` وتُعاد الجولة بالسياق الجديد.
- تنبيهات FCM عند اكتمال/انتهاء البحث الجزئي اختيارية ولا تؤثر على البحث إذا تعطلت.
- تسليم التنبيه يُتابع لكل جهاز على حدة: الجهاز الذي استلم لا يعاد تنبيهه، والجهاز الذي فشل مؤقتًا يعاد له وحده.

## البنية المختارة

- **Client:** Flutter (Android + Windows من قاعدة كود واحدة)
- **API:** FastAPI / Python
- **Database + queue:** PostgreSQL فقط، بدون Redis
- **Search:** SearXNG + HTTP crawler خفيف
- **Vision:** SmolVLM-256M محلي عبر llama.cpp
- **Planner:** Qwen2.5-0.5B Q4 محلي عبر llama.cpp
- **Media:** FFmpeg + Tesseract OCR + Whisper.cpp + ImageHash
- **Server:** Oracle Cloud Always Free Ampere A1
- **VPN:** WireGuard + Tinyproxy داخل السيرفر
- **Updates:** GitHub Releases + SHA-256 قبل التثبيت

## VPN

التشغيل العادي يعمل مباشرة. عند إضافة WireGuard client config وتشغيل `docker-compose.vpn.yml`:

- يخرج SearXNG عبر الـVPN.
- يمكن للـWorker التحويل بين direct وVPN للصفحات العامة.
- يدعم السيرفر مخارج Proxy مسماة إضافية مع sticky routing وcircuit breaker.
- لا يوجد تدوير IP عشوائي.
- 403/429/CAPTCHA لا تسبب تبديلًا تلقائيًا للمسار.
- مفاتيح WireGuard مستثناة من Git ولا ترفع إلى GitHub.

راجع `docs/VPN.md` للتشغيل.

## فلسفة استهلاك المجاني

1. لا يتم تحليل الفيديو frame-by-frame؛ تؤخذ لقطات تغيّر المشهد، ويستخدم fallback زمني فقط عند الحاجة.
2. Vision يطبق على عدد محدود من اللقطات.
3. Query Planner ينتج عددًا محدودًا من الاستعلامات ويستخدم cache.
4. نتائج البحث وتحليل الوسائط لها cache بإصدارات لمنع إعادة العمل غير الضرورية ومنع استخدام تحليل قديم بعد ترقية الخوارزمية.
5. المهام تستخدم PostgreSQL queue بدل Redis.
6. المرفقات الأصلية مؤقتة وتحذف عند نهاية البحث؛ لا يوجد Object Storage دائم في المسار الأساسي.
7. لا يوجد API ذكاء مدفوع ضمن المسار الأساسي.
8. لكل مهمة ميزانية موارد مع بحث على جولات وbackoff بدل إبقاء CPU مشغولًا بلا فائدة.
9. نفس المصدر لا يعاد فحصه بسبب معاملات tracking الشائعة.
10. صور النتائج محدودة الحجم وتُجلب عبر Egress الآمن بدل الاتصال المباشر من الجهاز بالموقع الخارجي.

راجع `docs/ARCHITECTURE.md` و `docs/FREE_TIER_BUDGET.md` للتفاصيل.


## Production

المستودع يحتوي الآن مسار إنتاج كامل:

- `docker-compose.prod.yml` يضيف Caddy وHTTPS تلقائي.
- `scripts/bootstrap_server.sh` يجهز Docker على Ubuntu.
- `scripts/validate_production_env.py` يمنع التشغيل بقيم افتراضية أو إعداد TLS/Firebase غير صحيح.
- `scripts/deploy_server.sh` ينشر بدون `down` ويتحقق من health ثم يحاول rollback عند الفشل.
- Workflow **Deploy Production** ينشر عبر SSH باستخدام GitHub Environment secrets.
- Workflow **Release** يدعم tag أو تشغيل يدوي لنسخة مثل `v1.0.0`.

التفاصيل في `docs/PRODUCTION.md`.
